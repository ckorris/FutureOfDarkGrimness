# 035 — Transport(X) system

**Status**: in-progress
**Related**: #042 (rule framework — Transport is a deferred *core* rule), #006 (Hero — closest precedent for a structural core rule), #033 (Caster — first consumer of embarked effective-position), #031 (Defense/unit rules umbrella lists Transport)

## Goal
Implement the **Transport(X)** special rule (GF Core v3.5.1): a vehicle unit that carries friendly units inside it. "Done" = units can be loaded **at deployment** (chosen then, not in the army creator), ride inside (off the table, untargetable), disembark and embark via move actions, and spill out — dangerous-terrain test + Shaken + placed within 6" — when the transport is destroyed. Capacity is X "spaces": a normal model takes 1; a Hero (Tough≤6) or non-Hero (Tough≤3) takes 3; models above those caps can't ride.

Rule text (v3.5.1):
> **Transport(X):** May transport up to X models, or Heroes with up to Tough(6) and non-Heroes with up to Tough(3) which occupy 3 spaces each. Transports may deploy with units inside, and units may enter/exit by using any move action, but must stay fully within 6" of it when exiting. Units inside/outside transports may not target other units outside/inside transports, but may target the transport itself. When a transport is destroyed, units inside must take a dangerous terrain test, are Shaken, and must be placed fully within 6" of the transport before it's removed.

## Decisions
- **Transport is a *core* rule, not a composed `Condition × Effect` data rule** — consistent with #042's explicit classification ("Tough, …, Transport, Aircraft, Hero live in C# as first-class concepts") and the Phase 6 deferral ("they land when the engine refactor defines the transport embark/disembark primitive"). The rule *declaration* stays abstract data (a `Transport` marker in `CoreRuleCatalog`, capacity = `Arg(0)`, resolved at army-load like every other rule); the *behavior* is a first-class engine subsystem. Exactly the Hero precedent (catalog marker + `HeroJoinResolver` engine code).
- **Embarked representation = off-table / reserve-style** (decided with the user). Occupant models stay at origin (off-battlefield); they're excluded from targeting / activation / objectives / melee *for free* via the existing `IUnit.GetIsOnBattlefield()` filter — the same primitive Ambush/Scout reserves use. The inside↔outside targeting restriction therefore falls out for free, and "may target the transport itself" is automatic (the transport is a normal on-table unit). The one carve-out: embarked units must re-enter the *activation* pool so they can disembark. **Rejected**: co-located + an `Embarked` flag threaded through every read site (the large-blast-radius problem Hero rejected for per-model stats); merge-into-transport (breaks the separate-unit semantics — "units inside may target the transport itself" implies distinct entities).
- **No bespoke state field on `UnitData`** (decided with the user). The occupancy relationship lives in the **token system** (#042's blessed state primitive — "no ad-hoc state fields scattered across the engine for rule purposes"): the occupant carries a cross-unit `EmbarkedIn` token whose `OwnerUnitID` is the transport. The transport stores **nothing** — its current load is a *derived query* over occupants' tokens; its capacity is the rule's `Arg(0)`. Save/load is free (tokens already round-trip). Trade: occupancy is recomputed on demand rather than stored (a cheap bounded scan at the few transport-relevant moments).
- **Load is chosen at deployment, NOT in the army creator** (decided with the user — specifically different from Hero's army-file `JoinsUnitId`). So there is **no** `UnitFileEntry.EmbarkInTransportId`; embarking a unit at deployment leaves it set-aside (off-battlefield) and stamps the `EmbarkedIn` token. Default decision point: transport-initiated load when the transport deploys (UX confirmed later — "UI later" per the user).
- **Destruction spillout = immediate, mid-combat** (decided with the user — the faithful reading of "before it's removed"). When the transport's last model dies, resolution is interrupted to place occupants within 6", run a dangerous-terrain test, and apply Shaken. A mercy of the off-table representation: the dead transport's models persist at their last position, so the wreck position is always readable for the 6" placement — the hard part is purely the flow interruption (slice E's own micro-fork).
- **Slice B flow = per-unit deploy action (`ChooseDeployActionStage`), not transport-initiated batch load** (decided with the user, 2026-06-21). The deployment-flow map showed `ChooseDeployActionStage` carries a standing TODO earmarking it for "place in a Transport", and a per-unit action mirrors the proven Ambush hold-or-deploy flow (the unit sets itself aside on its own turn → cleaner pool handling, no multi-select from the undeployed pool). Rejected transport-initiated load (would need pool-subset selection + transport-specific code in `DeployUnitStage`). This refines the earlier "transport-initiated when the transport deploys" default.
- **Slice C disembark flow (decided with the user, 2026-06-21):** (a) **carve-out** — embarked units join the activation pool so the unit disembarks on its own turn (OPR-faithful), over a transport-initiated unload; (b) **surfacing = data ability via the #010 offer path**, over engine-detecting the token in `ChooseActionStage` (the user "really doesn't like" the engine-detected version). Realized as a **durable universal** `Disembark` `ActivatedAbility` attached to every unit at army-load, gated by `AvailableWhen = TokenPresent(EmbarkedIn)` (so it's offered only when embarked, and self-clears when the token goes — no transient attach/remove, no `RemoveRuleDefinition`), routed specially by rule identity to a dedicated `DisembarkStage`; (c) **Advance-equivalent** — place within 6", counts as the move, may then Shoot; disembark-then-Rush/Charge deferred. **Durable over transient (decided 2026-06-21 after confirming save/load IS built — see #094):** a runtime-attached (transient) rule wouldn't survive a resume at all, whereas a universal army-load rule is restored by the general #094 fix and gated by the *serialized* `EmbarkedIn` token. Plumbing: a marker `Effect.Disembark` + by-name routing in `ChooseActionStage`.
- **Embarked effective-position is an opt-in seam, build deferred.** Generic position reads keep seeing origin (the whole point). A `GetEffectivePosition` resolver (embarked → transport's position) is provided for the rules that genuinely need it (Caster's "friendly caster within 18"" — #033, not yet implemented). Per no-speculative-generality, the resolver's *implementation* is deferred until its first consumer; the `EmbarkedIn` token already stores the link, so deferral costs nothing.

## Plan (slices; each: implement → integration test mirroring nearest *RuleIntegrationTests → verify → commit → ledger)
- **A. Foundation.** `Transport` catalog marker (capacity = `Arg(0)`); engine-known `EmbarkedIn` cross-unit token; `TransportUtilities` — capacity, 1-vs-3 space cost + Tough-cap eligibility, token-derived occupancy / remaining-capacity, embark/disembark token writes, off-table representation, effective-position seam. Unit-tested via `TransportUtilitiesTests`. *(in progress — TDD: tests authored first against a stubbed `TransportUtilities`; drive red→green next.)*
- **B. Deploy-time embark.** ✓ DONE. Per-unit deploy action in `ChooseDeployActionStage` (the stage the codebase earmarked for it): when the deploying unit can ride a friendly transport already on the table, the owner is offered a `SelectionRequest<UnitData>` of eligible transports (cancel = deploy normally). On embark → `TransportUtilities.Embark` + clear `CurrentDeployingUnit` + a new `OnEmbarked` binding skips placement and returns to the next player (mirrors Ambush hold's `OnDeferred`). When no transport is eligible there's no prompt — normal deployment is unchanged. Rides the existing GUI/CLI/AI `SelectionResolver<UnitData>` (no new resolver). Tested via `TransportDeploymentChoiceTests` (5 cases).
- **C. Disembark.** ✓ DONE. (design settled with the user 2026-06-21 — see Decisions). Three parts: (1) **activation carve-out** — `SingleRoundContext` admits embarked units to the unactivated pool (`GetIsOnBattlefield() || IsEmbarked`); (2) **Disembark surfaces as a data ability via the #010 offer path** — a `Disembark` `ActivatedAbility` at `Activation_OnActionChoice` carried by every unit (attached at army-load), gated by `AvailableWhen = TokenPresent(EmbarkedIn)`, so `ChooseActionStage.GatherOffers` lists "Disembark" only when embarked; the chosen offer is routed *specially* (by rule identity) to a new `DisembarkStage` rather than the generic token-op `CustomActionStage`; (3) **Advance-equivalent move** — `DisembarkStage` issues a place-within-6"-of-transport request, un-embarks (token + ability removed), then `RegisterMoveFinished(0f)` so the unit may still Shoot but not move again. Builds on master's #010 custom-action seam (merged in).
- **D. Mid-game embark.** An outside unit moves into a friendly transport with capacity and embarks.
- **E. Destruction spillout (mid-combat).** Detect transport death; interrupt resolution; place occupants within 6" + dangerous test + Shaken. The *deterministic* consequences (`ApplySpilloutEffects` = un-embark + Shaken + per-model dangerous test; `IsWithinTransportRange` = the within-6" constraint) are unit-tested in slice A's foundation; only the mid-combat orchestration + interactive placement remain for slice E's stage integration test.
- Effective-position resolver folds in whenever Caster (#033) lands.

## Deferred (recorded — not silently cut)
- **Disembark-then-Charge / exact Rush distance measured from the 6" drop point** — slice C treats disembark as an Advance-equivalent.
- **Visual "troops riding the hull"** — off-table representation; UI shows occupancy as a roster badge on the transport (the effective-position resolver would also feed a renderer that wanted to draw them).
- **Capacity-by-Tough mixed-unit hero nuance** — a unit containing both a Tough≤6 hero and Tough≤3 grunts: per-model caps apply per model; the integrated `CanUnitEmbark` hero-detection for mixed units is the corner to harden in slice A.
- **Army-load registration of `Transport`** — the marker is defined but intentionally **not yet in `CoreRuleCatalog.All`** (so the army-load resolver / registry / numeric-arity / picker aren't perturbed this slice; the `All` scope-partition test stays green). It joins `All` with scope + numeric-arity handling when slice B wires the deploy path. Until then tests reference `CoreRuleCatalog.Transport` directly.
- **Disembark survival across save/load depends on #094.** Save/load **is** built; the resume path doesn't re-attach `RuleDefinitions` (a systemic gap — **#094, HIGH PRIORITY**), so today a resumed embarked unit keeps its serialized `EmbarkedIn` token but loses the Disembark ability until #094 lands. The **durable universal** attach was chosen precisely so a minimal #094 fix (re-attach engine/universal rules on resume — no unit↔army-entry mapping needed) restores it. The same gap drops the `Transport` rule's capacity on resume, which will bite slice D (mid-game embark eligibility) — also resolved by #094.
- **Multiple units sharing one transport's capacity** — the rule allows it (plural "units inside"); `TransportUtilities` supports it (occupancy is a list) and it's covered in unit tests; verify end-to-end last.
- **Mid-combat spillout orchestration has no unit test (deferred to a stage integration test).** Interrupting combat resolution when the transport's last model dies, and issuing the interactive "place each occupant within 6" of the wreck" request, can't be exercised without the stage machinery — it's deferred to a slice-E `TransportRuleIntegrationTests` case driving the real stages (the project's standard for stage behavior). The deterministic consequences *are* unit-tested now: `ApplySpilloutEffects` (un-embark + Shaken + dangerous test), `IsWithinTransportRange` (the 6" constraint), and `GetOccupants` after the transport dies ("who spills").
