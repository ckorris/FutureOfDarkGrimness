# 093 — Per-model special rules: the general reckoning

**Status**: in progress
**Related**: #006 (Hero — forced the issue and bakes in the first per-model exceptions), #042 (rule framework — unit/weapon scope), #027 (weapon scope), #023 (Tough wound-priority), #031/#032 (rule implementations)

## Goal
Revisit, holistically, the engine's assumption that special rules are **unit-wide** (with weapon-scope the only exception). #006 is adding **per-model** rule/stat carriage as targeted exceptions for the Hero (per-model stats; per-model *combat* rules; weapon rules already per-model via the weapon). That patchwork is deliberate and bounded, but it leaves the general question unanswered and several corners deferred. This item is the reckoning: decide whether per-model scope should be a first-class, uniform capability across **all** hook categories, audit where unit-wide assumptions are baked in, and absorb the corners #006 punts.

"Done" = a coherent, documented scope model (unit / model / weapon) applied consistently by the dispatcher, the deferred corners below handled or explicitly and durably waived, and the #006 hero exceptions either subsumed by the general mechanism or confirmed as legitimately hero-specific.

## Why this exists (the worry to revisit)
The user flagged (2026-06-15) that doing per-model as hero-shaped exceptions risks biting us later — different code paths deciding "does this rule apply to this model?" in different stages, inconsistently. In OPR the tabletop truth is that rules/stats are **per-model**; unit-level is a shortcut for homogeneous units, and it's "a little loose" (units may have models that don't all share a rule). So the general direction is likely "unit-level default + per-model overrides, unioned by the dispatcher everywhere," not "hero special cases."

## What #006 bakes in now (the exceptions to revisit)
- **Per-model STATS** via `HeroStatRules` (Quality/Defense/wounds), read model-override-then-unit at exactly three stages (hit / save / morale). Generalizes cleanly but is currently reached only through hero-aware helpers.
- **Per-model COMBAT rules** via `ModelData.RuleDefinitions` + `ERuleScope.Model` + model-aware dispatch on hit/save/wound hooks (slice F). This is the seed of the general mechanism — make sure it's built general, not hero-only.
- **Hero-specific behaviors** that are NOT generic per-model and should stay special: wounds-last, morale-on-behalf (unit borrows a model's Quality), last-model Defense (a model *suppresses* its own stat until sole survivor). Confirm these stay layered on the Hero marker.
- **Weapon-scoped rules** already per-model (ride the weapon; `WeaponComparer` keeps a rule-bearing weapon its own batch). Already consistent — leave alone.

## Deferred corners #006 punts here
- **Per-model MOVEMENT rules** (Fast/Slow on one model, e.g. a joined hero): the move budget is unit-level. Needs per-model budgets and a coherency interaction (a faster model still can't break coherence). Movement-subsystem change. **[4a DONE — slice 4a, 2026-07-02: engine per-model budgets (`MovementActionContext.TryGetModelMoveBudget`) + per-model `MovementUtilities.ValidatePaths` + authoritative `DefinePathStage` enforcement; coherency still reins a fast model in. **4b remains**: request + GUI/CLI/AI resolvers still use unit scalars, so a Fast hero can't yet be *moved* ahead via the GUI (range rings + resolver UX = the app half).]**
- **Per-model ACTIVATED abilities** (a joined hero with Caster / Vanguard / Martial Prowess): the activation/offer layer assumes unit-level abilities; needs to offer/resolve a single model's ability inside a host unit. **Caster specifically handled 2026-06-25** (see Notes) — `IsCaster` and the round-start token grant are now model-aware, so a joined caster hero casts via the host unit's pool. Vanguard / Martial Prowess and a *general* per-model activated-ability mechanism remain. **[DONE — slice 3, 2026-07-02: `GatherOffers` reads per-model rules, so any per-model activated ability (Vanguard/Martial Prowess) is offered for the host unit; resolution stays unit-level, correct for these unit-affecting abilities.]**
- **Defensive / morale "all models have this rule" rules** (Stealth, Regeneration, Fearless): rule text gates on *every* model having it. With mixed-rule units this needs an explicit all-models check rather than "the unit has the rule." Audit these once models can carry rules independently. **[DONE — slice 2, 2026-07-02: `Condition.AllModelsHaveThisRule` now gates all three; a joined hero that doesn't natively carry the rule breaks it for the unit.]**
- **Unit-wide stat/rule read sites not yet audited**: any place that reads `unit.Quality`/`unit.Defense`/`unit.RuleDefinitions` assuming homogeneity. Catalogue them; route through the per-model-aware accessors.

## Deferred corners #006 punts here (cont.)
- **Impact(X) per-model** (a joined hero with Impact): fires on `Melee_OnChargeContact`, which is not weapon-batched and has no "firing model" concept, so it can't ride slice F's weapon-batch-owner dispatch. Needs a relevant-model resolution for charge-contact hooks (which models with the rule are in contact). Confirmed during slice F.
- **Dispatcher dedup keyed by `UnitID`, not `ModelID`** (`RuleEvaluator.DedupState`): argument-less rules fire at most once *per unit*. Fine while only one model (the hero) carries per-model rules, but a genuinely mixed unit (two models with the same argless rule) would wrongly collapse to one. Re-key to `ModelID` when per-model becomes general. **[2026-07-02 correction (slice 1): re-keying to `ModelID` is NOT the fix — it double-counts no-stack batch rules. `Effect.AddExtraHit` counts the whole pooled batch's 6s and `HitInjectionSink` sums firings, so firing an argless "don't stack" rule once *per model* doubles the extra hits; per-unit dedup is correct for those. The real bug was `WeaponBatchRuleOwners`' `Count == 1` gate suppressing a rule that *all* owners of a 2+-model batch share. Slice 1 fixed it with an explicit `AllOwners` intersection at the batch hooks, leaving dedup per-unit — see Decisions + the 2026-07-02 note.]**
- **`ERuleScope.Model` as an authoring level**: slice F deliberately does NOT add it (the merge moves rules onto a model in engine code, bypassing army-load scope validation). If models ever become army-file authoring targets, scope needs a Model level + loader support.

## Folded in: combat-kind condition (melee-only / shooting-only)
Originally spun off from the #015/#016 close-out as its own #093 ("combat-kind condition"); folded here on 2026-06-21 when a number collision surfaced at merge time (both items had independently claimed 093) and the two were judged close enough to live together as #042-framework refinements. Different axis from per-model *scope* (this is combat *kind*), but tracked here per that decision.

**Goal:** Make "applies in melee only" / "applies in shooting only" a first-class `Condition` in the #042 data-driven `Condition × Effect` system, so a rule (or the #015/#016 effect seams) can declare its combat-kind gating as data instead of hand-wiring an `IsMelee` check. "Done" = a rule definition can carry a combat-kind condition the `RuleEvaluator` honours, with at least one existing ad-hoc gate migrated onto it to prove the path.

**Background:** combat kind is already known at evaluation time — `IsMelee`/`IsCharging` are threaded through `HitRollModifierContext`/`HitRollCompleteContext` — but every rule that cares gates on it imperatively and individually: Indirect (`Not(IsMelee)`), Thrust (melee + charging), Furious's melee gate, #051's charging gate. That scatters the concept and makes new combat-kind-specific effects (the #015 attack-count and #016 per-hit-save seams) re-invent the gate.

**Pointers:** Conditions live under `Rules/Dispatch/` (`CoreRuleCatalog.cs`, `RuleEvaluator`); mirror an existing context-evaluated condition. The combat-kind flag is already on the contexts — a read of existing state, not new plumbing. Migrate Indirect's `Not(IsMelee)` first as the proof-of-path. Relevant to #015 (attack-count mods are often shooting-only, e.g. Rapid Fire) and #016 (per-hit save effects may be combat-kind-specific).

## Decisions
- 2026-07-02 — **Per-model movement = full per-model path budgets** (slice 4, chosen with the user over "slowest-governs min budget" and an "all-models gate"). Each model gets its own Advance/Rush/Charge budget (unit base + unit rules + that model's own movement rules); the path validator caps each model against its own budget, and coherency independently keeps a fast model from outrunning cohesion. The most faithful reading and a real movement-subsystem change; split into 4a (engine budgets + validation + authoritative enforcement) and 4b (request + GUI/CLI/AI resolver UX / per-model range rings).
- 2026-07-02 — **All-models gate: a joined hero doesn't inherit the host unit's unit-wide rules; aura/granted rules count as unit-level** (slice 2). `Condition.AllModelsHaveThisRule` is self-referential (reads the firing rule's own `Definition`), so one condition serves every "whole unit must have it" rule. A model has the rule if it's on the model's own list, or — for a *native* (non-joined) model — a static unit rule OR an aura/"gains rule X" grant (both project unit-wide). The joined hero (new `IUnit.JoinedHeroModelId`) counts only its own model rules (the merge relocated the hero's rules there; OPR heroes don't inherit the host's). Dead models are excluded (a ruleless hero dying restores the unit's rule). Granted rules are matched by canonical name — the alias resolver isn't reachable inside a condition; core auras grant the canonical name. Argument-agnostic (these three are argless); a future (X) variant would extend it.
- 2026-07-02 — **First slice = foundational per-model dispatch; scope = foundation + key corners** (both signed off by the user). Two forks resolved: (1) build the foundation now vs a concrete corner first vs a scope-doc first → **foundation**; (2) how much of the umbrella to land → **foundation + high-value corners (movement, defensive all-models, Vanguard offers), durably deferring the long tail** (`ERuleScope.Model` authoring, Impact(X) per-model, `PreApplyWoundContext` combat-kind, pooled-roll per-model attribution).
- 2026-07-02 — **Per-model dispatch is hook-dependent; make the mode explicit (`EModelRuleScope`).** Rather than one global rule for the `models` param, each call site declares `AnyOwner` (union — a rule belongs to individual models independently: the joined-Caster round-start token grant) or `AllOwners` (intersection — a rule modifies an indivisible pooled batch and applies only if every living owner shares it: the combat hit hooks). Chosen over (a) a naive `ModelID`-keyed dedup [double-counts no-stack batch rules — see the correction in the Deferred-corners section], and (b) union-everywhere [leaks one model's rule onto the others' pooled roll and flips the hero shared-weapon test]. `AllOwners` preserves all four hero stat/rule behaviors, fixes the multi-owner over-suppression, respects "instances don't stack," and hands the defensive "all-models" corner (Stealth/Regeneration/Fearless) the exact primitive it needs.

## Notes
- 2026-07-02: **Slice 4a (per-model movement budgets — engine) DONE.** `MovementActionContext` now computes each living model's own Advance/Rush/Charge budget (unit base + unit rules + that model's OWN movement rules, via the slice-1 AnyOwner model-aware evaluate) and exposes `TryGetModelMoveBudget`; a native model lands exactly on the unit scalars, so nothing changes for a unit with no per-model movement rules. `MovementUtilities.ValidatePaths` gained a per-model overload (`Func<ModelMoveEntry, ModelMoveBudget>`) — `ValidateOutOfMoveRange` / `ValidateChargeReach` cap each model against its own budget; the scalar overloads delegate with one budget for every model (unchanged). `DefinePathStage` authoritative re-validation uses per-model budgets (per-model hard cap = max(rush, charge − the unit-level Melee-Shrouding shrink)); `ValidateCoherency` still reins a fast model in independently. New `PerModelMovementBudgetTests` (5: context per-model budget / ranges-ahead accepted / uniform-cap rejects the lead / lower-cap rejects / coherency-still-binds). Engine suite **988/0**, build clean, headless exit 0 (×2). **Slice 4b (app) remains:** the `DefineMovementPathRequest` + GUI/CLI/AI resolvers still use the unit scalars, so a Fast hero can't yet be *moved* ahead via the GUI (rings show unit distance) and a Slow hero dragged to the unit distance would be rejected at the stage (no Slow-hero armies exist today — noted) — 4b threads per-model budgets to the resolvers + per-model range rings.
- 2026-07-02: **Slice 3 (per-model activated abilities — offers) DONE.** `RuleEvaluator.GatherOffers` now reads each LIVING model's per-model rules in addition to the unit's (extracted `GatherOffersFromRules`), so a joined hero's activated ability (Vanguard, Martial Prowess) is offered for the host unit — the merge already relocates such rules onto the hero model (`HeroJoinResolver`), it just wasn't read at the offer layer. AnyOwner union with a `(definition, ability)` `seen` set so an ability carried by both the unit and a model (or several models) is offered once (no-stack). Resolution (`ResolveAbility`) stays unit-level, which is correct for these unit-affecting abilities (the ability moves/buffs the whole unit, bearer = unit). Caster was already model-aware (2026-06-25 point fix); this generalizes the rest. New `PerModelActivatedAbilityTests` (4 cases via the real `GatherOffers` + merge harness: offered / not-offered / dead-hero / offered-once). Engine suite **983/0**, build clean, headless exit 0. Remaining agreed corner: per-model **movement** (`GetMobility`).
- 2026-07-02: **Slice 2 (defensive "all-models" rules) DONE.** Stealth, Regeneration, and Fearless — unit-wide rules the rulebook applies only if *every* model in the unit has them — now carry a new self-referential `Condition.AllModelsHaveThisRule` (gates on the firing rule's own `Definition` being present on every living model). Added `IUnit.JoinedHeroModelId` (→ `UnitData.HeroAttachment?.HeroModelId`) so the check can tell a native model (shares the unit's rules) from a joined hero (only its own). Behaviour change: a joined hero without the rule now breaks it for the unit (previously the unit kept the benefit); a hero that also carries it, or a homogeneous unit, is unaffected; a ruleless hero dying restores it. Aura/"gains rule X" grants count as unit-level (fixed 7 aura-granted-Regeneration tests that would otherwise be suppressed). New `AllModelsRuleGateIntegrationTests` (4 cases via the real `CoreRuleCatalog.Stealth` + `RuleEvaluator`); engine suite **979/0**, full build clean, headless exit 0. The intersection primitive from slice 1 wasn't reused directly (this is a unit-level gate, not a batch-owner intersection), but the two share the "per-model rule membership" mental model. Next slice (TBD): per-model **movement** (`GetMobility`) or `GatherOffers` model-awareness (**Vanguard**).
