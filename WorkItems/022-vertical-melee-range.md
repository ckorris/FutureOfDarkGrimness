# 022 — Vertical melee range handling (`ChooseMeleeDefenderStage` TODO)

**Status**: done 2026-06-25 — engine suite 768/0, headless exit 0. No "Awaiting verification" hold (no-op at runtime today; see Outcome).
**Related**: #017 (melee in-range checks — built `MeleeRangeUtilities` 2"/4" cylinder), #018 (pile-in)
**Branch** (both repos): `022-vertical-melee-range` — submodule + superproject branched from master.

## Goal
The melee-range rule (GF v3.5.1) is a *cylinder*: two models engage if within **2" horizontal AND 4" vertical** base-to-base. `MeleeRangeUtilities.IsModelInMeleeRange` already implements this correctly (built under #017 for the post-pile-in strike/strike-back gate). "Done" = the *other* melee-range gates — which currently apply only the horizontal 2" half and ignore the 4" vertical ceiling — use the same cylinder, so a unit that is within 2" horizontally but beyond 4" vertically (e.g. on a tall ledge) is consistently treated as out of melee range everywhere.

## Notes
- **2026-06-25 — implemented (both gates).** Made the melee cylinder a single source of truth: new `MeleeRangeUtilities.AreModelsInMeleeRange(IModel, IModel)` (the 2"/4" conjunction) + `AreUnitsInMeleeRange(IUnit, IUnit)` (any living-model pair in range). The existing `IsModelInMeleeRange(ModelData, …)` (the #017 strike gate) now delegates to `AreModelsInMeleeRange`, so all three gates share one definition. Wired `AreUnitsInMeleeRange` into both `ChooseMeleeDefenderStage` (defender eligibility — closed the TODO) and `ChooseActionStage.GetCanCharge` (charge availability), replacing the horizontal-only `MinDistanceBetweenUnits(includeVertical:false) <= MELEE_RANGE_INCHES_HORIZONTAL` checks. `using FDG.Utilities;` left in both files (harmless; other code may rely on it; not worth churn).
- **Tests:** new `VerticalMeleeRangeTests` — 5 predicate cases (horiz+vert in range; horiz-in/vert-out = the #022 case; vertical exactly at 4" ceiling; horiz-out; dead-model ignored) + 2 stage-integration cases through the real `ChooseMeleeDefenderStage` (vertically-distant enemy → routes to `BackToChooseAction`, not offered; in-cylinder enemy → single-candidate fast path selects it, no requester). `GetCanCharge` is a *private instance* method so it isn't unit-tested directly; it's a one-line delegation to the same predicate, covered transitively by the predicate tests. Suite 761→768/0; headless exit 0 (full 4-round game, melee resolved).
- **2026-06-25 — investigation.** Found the gap is broader than one TODO but small. Three "is an enemy in melee range" gates exist:
  1. `ChooseMeleeDefenderStage.cs:53-57` — defender eligibility. Uses `MinDistanceBetweenUnits(..., includeVertical:false) <= MELEE_RANGE_INCHES_HORIZONTAL`. The TODO ("Deal with vertical, but we might leave that for pile-in") lives here.
  2. `ChooseActionStage.GetCanCharge` (`ChooseActionStage.cs:319-322`) — Charge-action availability. Identical horizontal-only pattern.
  3. `MeleeRangeUtilities.IsModelInMeleeRange` — the post-pile-in strike/strike-back gate. **Already correct** (2"/4" cylinder).
- **Key subtlety:** neither `includeVertical` mode of `MinDistanceBetweenUnits` implements the cylinder. `includeVertical:false` ignores the vertical ceiling (over-includes); `includeVertical:true` computes a 3D *sphere* `sqrt(h²+v²) ≤ 2` (would wrongly exclude a model 0" horiz / 3" vert, which is in range per the 4" vertical rule). The correct primitive is the per-model conjunction already in `MeleeRangeUtilities` — so the fix is to add a unit-level wrapper there and call it from gates 1 (and 2).
- **No runtime behavior change today:** the user notes there is currently no way to move models vertically, so every `Position.y == 0` and vertical distance is always 0 ≤ 4. This is a correctness/consistency fix that becomes load-bearing when vertical movement lands; it is a no-op on the current ground-plane game, hence low risk.
- **Out of scope (left horizontal-only deliberately):** `MovementUtilities` charge-reach / standoff checks (`:236, :449, :632`) are 2D movement-geometry on the table plane, not the engagement cylinder — reaching a vertically-distant enemy is a movement concern that doesn't exist yet.

## Decisions
- **Scope = both gates** (user call 2026-06-25). Fix `ChooseMeleeDefenderStage` *and* `ChooseActionStage.GetCanCharge` via one shared unit-level predicate in `MeleeRangeUtilities`, so all three melee-range gates share the 2"/4" cylinder. Rationale: fixing only the defender stage would leave Charge able to light up while no defender is selectable for a vertically-distant enemy — a confusing dead-end.
- **New predicate, not a `MinDistanceBetweenUnits` flag.** Neither `includeVertical` mode expresses the cylinder (false = no vertical ceiling; true = a sphere that wrongly excludes a model directly below within 4"). The per-model conjunction in `MeleeRangeUtilities.IsModelInMeleeRange` is the correct primitive, so a unit-level wrapper there is the natural home.

## Outcome
Shipped 2026-06-25. The melee-engagement cylinder (2" horizontal AND 4" vertical) is now defined once in `MeleeRangeUtilities.AreModelsInMeleeRange` and consumed by all three gates — charge availability (`ChooseActionStage.GetCanCharge`), defender eligibility (`ChooseMeleeDefenderStage`), and the post-pile-in strike check (`IsModelInMeleeRange`, #017) — via the new unit-level `AreUnitsInMeleeRange` wrapper. The two former gates applied only the horizontal half; they now reject a unit that is within 2" horizontally but beyond 4" vertically, so Charge grays out exactly when no defender is selectable and the player can no longer be offered a defender no model could strike. 7 new tests; suite 768/0. **No deferrals.** **No "Awaiting verification" hold:** there is no vertical model movement in the game yet (all `Position.y == 0`), so the vertical ceiling never bites today — this is a correctness/consistency fix that becomes load-bearing when vertical movement lands, with no observable in-app behavior change to eyeball. Movement-geometry checks in `MovementUtilities` (charge-reach/standoff) were deliberately left horizontal-only (table-plane movement, a separate concern from the engagement cylinder).
