## 1. Overall architecture & project layout

The engine is a layered, interface-driven library: a data store at the bottom (`Data/`), game objects and an observable world view above it (`GameObjects/`, `TableState/`), a hierarchical stage state machine that *is* the rulebook (`StateMachine/`), a request/resolver brokerage for all player decisions (`StageResolution/`), and orthogonal channels for narration (`TextInterface/`, `Presentation/`) and replication (`Network/`, `MessageBus/`, `SaveLoad/`). The front end (Raylib app) plugs in only via interfaces: `IFDGGame`, resolver registries, sinks.

### Pros
- **The decision pipeline is the unifying idea, and it's a good one.** Every player decision — human-GUI, human-CLI, AI, or remote network player — flows through the same `IStageTaskRequest<TReply>` → resolver path. The engine genuinely doesn't know or care who is answering. This is the property that made AI players and networked play cheap to add, and it shows real architectural discipline.
- **Engine/front-end separation is real, not aspirational.** No Raylib/ImGui types leak into the engine; pacing is engine-owned but render-agnostic (`IPresentationClock`); CLI and GUI parity is maintained. Many hobby engines claim this split; this one actually has it.
- **One serialization spine.** The store's JSON settings (`GameDataStore.GetJsonSettings()`) are reused by the message bus, the request system, and save/load, so there is a single source of truth for how game data becomes text. That's why save/load and networking share so much machinery.
- **Subsystem lifecycles are managed**: the retired `TempVisuals/` system was excluded from compilation with a `_RETIRED.md` explaining what replaced it and how to resurrect — exemplary handling of dead-but-instructive code.
- Doc comments on newer code (Presentation, SaveLoad, IDs, GameProgressData) are excellent — they explain *why*, state serialization contracts, and reference work items.

### Cons → recommendations
- **Tests, mocks, and the test SDK live inside the shipping library.** `FutureOfDarkGrimness.csproj` references `Microsoft.NET.Test.Sdk`, `NUnit`, `Moq` — every consumer of the engine transitively pulls the test stack, and `Tests/` (9.5k lines) compiles into the game assembly. → *Split `Tests/` into a `FutureOfDarkGrimness.Tests` project. Mechanical, ~an hour, removes a whole class of dependency noise.*
- **Namespace identity crisis.** Most code is `FDG.*` (the declared `RootNamespace`), but `TableState/DataState.cs` and the lobby files are `FutureOfDarkGrimness.*`, and `FDGGame_AsClient` was `F.GameModel` (typo — fixed, see §13). → *Pick `FDG.*` and sweep the stragglers; it's a rename-only change but touches parent-app `using`s, so do it in one dedicated commit.*
- **Dependency cruft in the csproj**: both `SixLabors.ImageSharp` *and* `System.Drawing.Common` (Windows-only on .NET 8+ — it throws at runtime on Linux if ever used) are referenced, with a commented-out duplicate ImageSharp line and a "TODO: Put this back". → *Keep ImageSharp, drop System.Drawing.Common, delete the commented line.*
- **Mixed maturity is invisible from the outside.** Fully-implemented systems (presentation, rules dispatch) sit next to silent stubs (`RangeCheckStage`, fatigue/morale). A stage *existing* tells you nothing about whether the rule is enforced. → *Adopt a convention: stubs log a recognizable `[STUB]` prefix via `ITextOutput` (several already log "skipping, for now"), and keep the CLAUDE.md "known stubs" list fresh — it had drifted in four places (see §13.12).*
- Two essentially-dead subsystems linger: `Components/` + `FDGEntity` (an entity-component bag nothing instantiates) and most of `Special Rules/` (§8). → *Delete `FDGEntity` and `Components/IComponent`; keep `IPlayerOwnable` (used) wherever it fits best.*

### Novelty
The overall shape — store-backed observable world + hierarchical state machine + brokered decision requests — is a coherent, somewhat uncommon combination, but each piece is a known pattern. The decision brokerage is the most distinctive element.

**Score: 6/10** — strong skeleton and real separation of concerns, dragged down by hygiene (tests-in-library, namespaces, dead systems, stale docs).

## 2. Data layer: GameDataStore, DataBinding, Components

`GameDataStore` maps registered types to fixed-capacity `ComponentStore<T>` arenas. Entries are addressed by `DataReference` (TypeID + index + generation); `DataBinding<T>` is a live handle with change events; every create/update/remove also surfaces as a JSON event for replication. You called the design "a weird pseudo-ECS without the performance benefits" — that's accurate as far as it goes, but the assessment below is that the store *does* earn its keep, just not for the reason an ECS usually would.

### Pros
- **The store is the engine's replication and persistence surface, and that's its real value.** Because all mutable world state lives behind `Create/SetValue/Destroy`, you got three features almost for free: network sync (JSON change events → `AddSingleData`/`UpdateSingleData` messages), whole-game save (`GetAllDataReferencesAsJson`), and the observable `TableState` façade. A plain object graph would have needed bespoke dirty-tracking for each.
- **Generational references are genuinely good defensive design.** Stale handles fail loudly with a reason enum instead of silently reading recycled slots, and the index-0 `UnreferenceableTypeStruct` placeholder (so a default `TypeID` can't alias a real type) shows thoughtful failure-mode thinking.
- The builder + `CreateFromTypeMap` overloads (default map vs. save-restored map with recorded capacities) are clean, and the "new types must be appended last" comment documents the compatibility contract.
- `DataBindingJsonConverter<T>` — bindings serialize as bare `DataReference`s and rehydrate against the local store — is the right call and what makes cross-machine references work at all.

### Cons → recommendations
- **Fixed capacities are a latent crash in real games.** `ComponentStore<T>` never grows; `Create` throws `ExceededDataTypeCapacityException` when full. The default map registers `ModelData` at **64** and `Position` at 128 — two 40-model armies (perfectly normal GDF lists) exceed both, crashing at army creation. Nothing warns before that. → *Either make stores growable (doubling is fine — nothing holds raw indices across a grow except `DataReference`s, which stay valid since index/generation don't move), or raise capacities (e.g. 512/1024) and add a startup assert that estimates army size against capacity. The save format already records capacities, so growth is backward-compatible.*
- **The ECS costume buys nothing.** Data is stored as whole OOP objects (`ModelData` with lists, events, visual providers) in arrays — no SoA layout, no archetype iteration, no cache benefit; meanwhile you pay the ECS costs: positional type IDs, capacity ceilings, reflection-driven store construction (`MakeGenericMethod` per type), and a parallel `Dictionary<int, DataBinding<T>>` per store. → *Don't rip it out — the replication surface is load-bearing — but simplify the costume: (a) key the type map by stable string name rather than registration position (kills the "append only at the end" trap; the save file already stores `FullName`s, so this mostly means using names as the wire/save key); (b) drop per-type converter instances in favor of one non-generic converter that handles any `DataBinding<>` via the store; (c) delete the linear `Create` scan in favor of a free-list if capacity grows.*
- **Positional `TypeID` is a compatibility trap.** Registration order is silently part of the save format and the wire format. One reordered `RegisterType` call invalidates every existing save with a confusing generation/type error. → *Covered by the name-keyed map above; until then, add a unit test that pins the exact default type-map order so a reorder fails CI loudly.*
- **No thread-safety statement.** The store is mutated from the engine thread and read (and on clients, written via `SetValueWithJson`) from bus dispatch threads. `ComponentStore` arrays and the bindings dictionary are unguarded. With the current "engine continuations run on the bus thread" behavior (§5) this mostly accidentally serializes, but it's luck, not design. → *Document the intended threading model, and either lock the store's public surface (cheap at this scale) or funnel all mutations through one logical thread.*
- **Update chattiness**: every `SetValue` on the host serializes the whole value to JSON (when a subscriber exists) — a `ModelData` update re-serializes its weapons, rules, and token container to move one model. Irrelevant for performance at this scale, but it also means *value types containing object references replicate by value snapshot*, which is a correctness subtlety worth a comment.
- Cruft (logged in §13): the never-used `_setValueCache` field, the unused private parameterless constructor with "TODO: Initialize converters?", and `GameDataStoreBuilder.RegisterType` computing a `typeID` and normalizing `capacity` *after* already adding the entry (both dead).

### Novelty
Generational-index arenas ("slotmaps") are standard in ECS/Rust circles, rare in C# game code — recognizable, not exotic. The interesting twist is using the store as a replication boundary rather than for iteration performance; that resembles how some networked games treat "replicated properties" (Unreal-style) more than an ECS.

### Test coverage notes
Round-trips are covered (`MessageSerializationTests`, `GameSaveLoadTests`), but the store itself has no direct tests for: capacity exhaustion, generation reuse after `Destroy`, `IsValid` reason codes (one was wrong — §13.2), or concurrent access. A small `GameDataStoreTests` file would pay for itself.

**Score: 5/10** — defensible core idea with real payoff, but the capacity ceiling is a time bomb, the positional type map is fragile, and the ECS machinery is cost without benefit.

## 3. Game objects & TableState

`ModelData`/`UnitData`/`ArmyData`/`TeamData` are the world objects, fronted by `IModel`/`IUnit`/etc.; `TableState` wraps the store in per-type observable views (`OnObjectCreated`/`OnObjectRemoved` + `Objects`); `GameProgressData` snapshots round/turn flow for save-resume.

### Pros
- **The ID story is excellent.** `ModelID`/`UnitID`/`PlayerID` as `readonly record struct(Guid)` give type-safe, serialization-stable identity, with doc comments that explicitly distinguish them from store-local `DataReference`s and state what survives a round-trip. This is exactly how to do strongly-typed IDs in C#.
- `TableState`/`DataState<TInterface, TDataObject>` is a tidy ~50-line façade: renderers subscribe to world changes without ever seeing the store.
- `GameProgressData` is a model citizen: thorough docs, team-by-number (stable) rather than by reference, bindings for units, an explicit resume-stage enum.
- `UnitData.RewireModelWoundSubscriptions` and its comment show hard-won understanding of the deserialization-order problem (the `[JsonConstructor]` path deliberately never calls `GetValue()`), which is the kind of contract that prevents whole bug classes.

### Cons → recommendations
- **`ModelData` is four things in one class**: serialized stats, live store handles, gameplay behavior (`DealWounds`), and *visual asset providers* — `MeshProvider` constructs a new OBJ provider object **on every property get** (and `MaterialProvider` builds a texture+material pair per access). → *Move visual lookup behind a front-end-side `IModelVisualResolver` keyed by ModelID (or at minimum cache the providers in private fields). The engine shouldn't own mesh selection at all once models aren't all SillyMan.*
- **`UnitData.Models` allocates a new `List<IModel>` (LINQ select+cast+ToList) on every access**, and it's accessed in loops everywhere (`RemainingWounds` iterates `Models` per model wound event, making wound application O(models²) with allocations). Harmless today, but it also means `unit.Models != unit.Models` reference-wise — a foot-gun for anyone caching. → *Expose `IReadOnlyList<DataBinding<ModelData>>` plus an enumerator that doesn't materialize, or cache and invalidate on membership change.*
- **Legacy rule plumbing still hangs off the objects**: `ModelData.SpecialRules`/`UnitData.SpecialRules` (old system, §8) sit beside `RuleDefinitions` (new system). `CalculateTotalWounds` returns a hardcoded 1 with a TODO even though Tough is actually applied later via `UnitCreationRules` — misleading to readers. → *Once §8's migration completes, delete the old lists and the dead calculation; until then add a one-line comment pointing at `UnitCreationRules`.*
- **The `(0,0,0) = unplaced` convention** (`GetIsOnBattlefield`) is shared invisible knowledge across engine, renderer, and AI; a model legitimately moved to exact table origin would vanish from "on battlefield" logic. Edge-case-unlikely, but conventions like this rot. → *Add an explicit `IsPlaced` bool (one more store field or a token) and keep the position check only as a migration shim.*
- Weapon distribution when loading army files (`UnitData(PlayerID, UnitFileEntry, …)`) sorts weapon entries by quantity and deals them round-robin — a reasonable approximation, but silently different from what a player might expect ("the sergeant has the plasma"). → *Fine for now; note it in army-file docs.*
- Cosmetics: ~40 lines of commented-out old `Model` class in `IModel.cs`; hardcoded 28mm base diameter with magic float `1.1023622f` → *name it `GameWideConstants.DEFAULT_BASE_DIAMETER_INCHES_28MM`.*

### Novelty
Standard interface-segregated domain model; the record-struct ID pattern is current best practice. Nothing exotic — which is right for this layer.

### Test coverage notes
`ModelIDTests`/`UnitIDTests`/`IUnitWeaponsTests`/`ObjectiveOwnershipTests` cover identity and helpers. Untested: `UnitData` wound-event aggregation (`OnModelWoundsDealt` math), `GetIsOnBattlefield` edge cases, weapon distribution from file entries.

**Score: 6/10** — strong IDs and observability, weakened by the god-object tendencies of `ModelData`, per-access allocation patterns, and half-removed legacy fields.

## 4. Stage machine

`StageBase<TContext>` / `ParentStage<TSelf, TChild>` form a hierarchical state machine: parents declare children and string-keyed transitions via `TransitionSetBuilder`, child contexts carry phase state downward, `ReconcileChildContextBeforeLeaving` harvests results upward, and `GetResumeEntry` lets a parent re-enter mid-tree on load. 70+ concrete stages mirror the GDF turn structure (setup → deployment → 4 rounds of alternating activations → victory).

### Pros
- **The hierarchy mirrors the rulebook 1:1**, which makes the game's flow legible from the directory tree alone (`MainPhaseRoundStage/SingleRoundStage/SingleTurnStage/MainUnitActionStage/ShootStage/FireStage/RollToHitStage/…`). For a rules engine, that navigability is worth a lot.
- Coverage is much better than CLAUDE.md suggests: ~76% of stages do real work, including complete terrain placement (3 modes with validation), D3+2 objective placement with auto-place debug mode, deployment with defer/Ambush/Scout, full ranged pipeline with LoS and majority-cover, melee winner/consolidation, and working victory calculation. Since the April survey, objective/terrain setup and PileIn went from stub → implemented.
- The save-resume hooks (`GetResumeEntry` + named top-level entry in `StateMachine.Enter`) integrate load-game into the machine without a parallel code path.
- `CombatStage`'s result-object pattern (each sub-stage produces a typed results struct that downstream stages query from context) keeps the combat math testable — the rule integration tests exploit exactly this.

### Cons → recommendations
- **The async chain is broken at every transition — this is the section's big structural flaw.** `Transition` is `delegate void`, but `TransitionSetBuilder.AddChild` registers `async (context) => await TransitionToChild(...)` — an **async-void** lambda. Consequences: (1) any exception thrown in a stage after the first transition is unobservable (async-void exceptions go to the synchronization context / crash the process rather than faulting a Task someone awaits); (2) the `Task` returned by `StateMachine.Enter` completes long before the game ends, so nothing can await "the game"; (3) `StageBase.SignalEvent` discards `ExecuteTransition`'s Task entirely. The system *works* because resolvers' `TaskCompletionSource`s keep the chain alive, but failure behavior is luck. → *Make `Transition` return `Task`, await it through `ExecuteTransition`/`SignalEvent`/`Activate`, and have the driver (`FDGServer`) await one end-to-end Task with a top-level try/catch that surfaces engine faults to the UI. This is the single highest-value refactor in the engine (medium effort: mechanical signature change through ~70 stages, but the compiler does the finding).*
  - Note the related stack behavior: with `InstantPresentationClock` and synchronous resolvers (tests, piped CLI), continuations run inline, so call-stack depth grows with every transition across a whole game. Tests pass today; a longer game format or deeper nesting could hit stack limits. Awaiting through with `Task.Yield` at round boundaries (or queueing transitions in a loop) fixes this for free during the same refactor.
- **String-keyed transitions** (`Bind(eventName)` → dictionary lookup, `KeyNotFoundException` with no message at runtime) — typos compile. The builder's `out`-parameter idioms (`AddChild(stage, out stage)`, `AddSibling(name, binding, out name)`) are clever but read as ceremony. → *Small win: include the event name and stage in the `KeyNotFoundException` message. Larger win (optional): replace string events with `StageBinding` object identity — the bindings already exist.*
- **Copy-paste pairs**: `DetermineInRangeAttackersStage`/`DefendersStage` are identical stubs; melee and ranged each have near-identical weapon-option building; two `BuildTargetListStage` generics. → *Extract a shared `WeaponOptionBuilder`; collapse the in-range pair into one parameterized stage when implementing range checks.*
- **Commented-out corpses**: ~150 lines of the old deploy-handler pattern in `DeployAllUnitsStage`, ~30 in `ArmySetupStage`, old event code in `AssignWoundsStage`. → *Delete; git remembers.*
- **Known rule gaps** (unchanged from survey, confirmed): melee range checks skipped (everyone fights), `RangeCheckStage` returns empty results (range is only enforced at weapon-option building), fatigue and melee-morale-penalty no-ops, morale modifiers TODO, `ChooseActionStage` custom actions hardcoded false, Deadly weapon-priority TODO. These are roadmap items, not defects — but see §13.12 for keeping the stub list honest.
- `MainPhaseRoundStage` resume assumes `PopulateTransitions` ran before `GetResumeEntry` (true today via ctor order, fragile under refactor). → *Assert `_singleRoundStage != null` with a clear message.*

### Novelty
Hierarchical state machines for turn structure are standard (HSM / statecharts); building one bespoke rather than using a library is normal for this domain because the contexts are the valuable part. The results-struct accumulation inside combat parents is a nice, slightly distinctive touch.

### Test coverage notes
Stage tests exist where logic is dense (`ConsolidateStageTests`, `ChooseRangedAttackStageTests`, `ObjectiveOwnershipTests`, `PileInTests`, `GameProgressTests`) and the doubles make new ones cheap. Untested but implemented: `VictoryCalculationStage` (winner/tie tally — pure logic, very testable), `StartOfRoundExtraActionStage` reserve arrival, `DetermineMeleeWinnerStage`. The transition machinery itself (`ParentStage` enter/exit/reconcile ordering) has no direct tests — worth adding before the async refactor so behavior is pinned.

**Score: 6/10** — expressive, legible structure with strong recent progress; the async-void transition chain is a serious latent-failure design flaw, and dead code/stub asymmetry needs grooming.

## 5. Stage resolution (requests/resolvers)

When a stage needs a player decision it builds an `IStageTaskRequest<TReply>` and awaits `context.PlayerRequester.RequestDecision(...)`. On the host, `RequestMessageSender` serializes the request, broadcasts it with a `TaskID`, and parks a `TaskCompletionSource`; each player's `NetworkedRequestMessageReceiver` (one per local player too — local and remote players use the *same* path) filters by `PlayerID`, dispatches to that player's `StageResolverRegistry`, and replies with JSON. `OutstandingTaskLister` mirrors pending tasks for "waiting on Player 2…" UI; errors round-trip as `StageTaskRequestErrorMessage`.

### Pros
- **This is the engine's crown jewel.** One abstraction gives you: CLI play, GUI play, AI play, hotseat (multiple local receivers), and networked play with zero per-mode engine code. The GUI resolver overlay, the AI registry, and piped-stdin automation all hang off the same seam. It's the part of the codebase I'd preserve at all costs.
- The JSON delegate registry (`_jsonResolverDelegates` keyed by request type full-name, whitelist semantics, typed deserialize→resolve→serialize round trip) is tight, and the comment explaining `typeof(TReply)` + `TypeNameHandling.Auto` for polymorphic replies (`CancellableResult<T>`) shows the wire contract is understood, not accidental.
- Error handling is two-sided: client resolver exceptions become `StageTaskRequestErrorMessage` → host fails the awaiting Task with a descriptive exception, instead of hanging the game.
- The awaiting/resolved notification ordering bug (notify-before-request so synchronous AI replies can't race the lister) is *documented in a comment* — exactly the kind of invariant that needs prose.
- `CancellableResult<T>`/`CancellableSelectionRequest` formalize the Back-button sentinel that earlier code handled with bare nulls; tests cover them.

### Cons → recommendations
- **`_pendingTaskAndResolvers` is mutated from two threads with no lock** (`RequestDecision` on the engine thread adds; bus-dispatch thread removes on reply). Dictionary corruption under concurrent requests (hotseat + AI, or multiple clients) is possible. → *`lock` the three touch points or use `ConcurrentDictionary<TaskID, …>` — five-minute fix.*
- **Replies resume the engine on the network thread.** `TaskCompletionSource.SetResult` without `RunContinuationsAsynchronously` runs the awaiting stage's continuation synchronously inside bus dispatch — so engine logic executes on the socket read loop until its next await, blocking further message processing and inviting re-entrancy. → *Create all TCSes with `TaskCreationOptions.RunContinuationsAsynchronously` (one-line each) — this also de-fangs several "engine runs on bus thread" hazards noted elsewhere.*
- **Requests are broadcast to all clients** and filtered receiver-side by `PlayerID`. Every player receives every other player's decision payloads (fine for GDF's open information, but it bakes in an assumption — hidden-info mechanics or lobby spectators would leak), and it's free bandwidth. → *Route requests via `SendCommandToSingleAsync` using the slot's connection (the per-player presentation sinks already prove the plumbing exists). Low urgency.*
- A reply for an unknown `TaskID` **throws inside bus dispatch** (`OnReceivedReplyMessage` → `ArgumentException`), which — given §6's lack of dispatch try/catch — can kill a client's read loop on a duplicate/late reply. → *Log-and-ignore unknown TaskIDs (idempotency), throw only in DEBUG.*
- Cosmetics: dead `_gameDataStore` field in `StageResolverRegistry`; exception text "Remove client returned an error" (→ "Remote"); commented-out player-ID filters in the two `OnReceived*` handlers should be deleted.

### Novelty
Async request brokering with serialized polymorphic payloads over a uniform local/remote bus is the most distinctive pattern in the codebase — it resembles a tiny RPC/mediator hybrid purpose-built for turn games. Standard ingredients, uncommon and effective combination.

### Test coverage notes
`RequestSystemTests` (9 tests) covers registration/resolution/error flow with a mock bus; `ConcreteRequestTests`, `CancellableResultTests` cover payloads. Gaps: concurrent request stress (two pending tasks, replies out of order), duplicate replies, and JSON round-trips for the request types *not* exercised by stage tests (`DefineMovementPathRequest`, `PlaceObjectsRequest<T>`, `AssignWoundsRequest` reply paths).

**Score: 8/10** — the best engineering in the engine; loses points only for thread-safety gaps around the pending-task table and continuation scheduling.

## 6. Networking & message bus

TCP host/client (`FDGHost`/`FDGClient`, port 6389) with a magic-number + length-prefix frame (`CommandProtocol`), a type-name + JSON payload envelope (`MessageSerializer`), and a type-keyed pub/sub bus (`MessageBusHost_Networked`/`MessageBusClient_Networked`) that the lobby, data sync (`GameDataUpdateSender/Receiver`), request system, chat/log relays, and presentation all ride.

### Pros
- **The wire format is simple and debuggable**: magic numbers catch desync immediately, `ReadExactlyAsync` handles partial reads correctly, payload length is validated non-negative, and `ArrayPool` keeps receive allocations flat.
- **Full-state client bootstrap is clean**: client builds the same default store, requests `AddAllDataMessage`, and replays reference+JSON pairs through the same converters used everywhere else. Store changes stream as add/update/remove messages keyed by `DataReference` — replication falls out of the data layer (§2's payoff).
- The bus registering a message type *at handler registration* (`RegisterForMessageEvent<T>` also whitelists `T` in the serializer) keeps send/receive registries in sync by construction on each side.
- Lobby flow (greeting → PlayerID assignment → player-list/settings/chat broadcasts → launch) is complete and works, including the resume-lobby re-crew path.

### Cons → recommendations
- **No per-connection write lock — concurrent sends can interleave frames.** `WriteCommandAsync` makes three separate `WriteAsync` calls (magic, length, payload). Host-side, data-update events, presentation beats, request broadcasts, and log relays can all send concurrently to the same `NetworkStream`; two interleaved frames corrupt the stream irrecoverably (next read sees wrong magic). Today you're mostly saved by accident — engine continuations run on the bus thread (§5), serializing most traffic — but `RunContinuationsAsynchronously` (recommended above!) or AI hosts will surface it. → *Add a per-connection `SemaphoreSlim(1,1)` around frame writes (or a per-connection outbound queue + single writer task). Do this in the same change as the §5 TCS fix, since that fix removes the accidental serialization.*
- **Silent message discard on unregistered types** (`MessageSerializer.DeserializeMessage` → `Debug.WriteLine` + `null`). The comment says "not everyone cares about every message" — legitimate for *broadcasts* (clients ignore host-only messages), but it also swallows version skew: a host sending a beat type an old client doesn't know produces… nothing. → *Keep the tolerant behavior but split the cases: maintain a set of deliberately-ignored types per side; unknown types log a visible warning (once per type) through `ITextOutput`, not `Debug`.*
- **A throwing handler kills the connection.** Bus dispatch has no try/catch; exceptions propagate into `HandleClientAsync`'s catch-all, which closes that client. Combined with §5's unknown-TaskID throw, one stray message can disconnect a player. → *Wrap `DispatchToHandlers` per-handler in try/catch with logging. Few lines, large robustness gain.*
- **`_lastMessageConnectionID` is a data race.** Each connected client has its own read loop; with 2+ remote clients, two dispatches can overlap and `GetCurrentMessageConnectionID` (used to answer the data-dump request and lobby greeting) can return the *other* client's connection — misrouted full-state sync. → *Pass `ConnectionID` through dispatch as a parameter (extend the registrar callback signature) instead of ambient state. Medium-small.*
- **No reconnect/resume**: an IO hiccup closes the client permanently; the host just removes it. Mid-game disconnect = player gone (their requests will hang forever — `RequestDecision` has no timeout either). → *Roadmap item: at minimum, fail pending requests for a disconnected player's slot and surface "player disconnected" to the stage layer (an AI-takeover hook would be a natural fit given §10).*
- **No version/type-map handshake.** Both ends assume identical builds (same default type map, same message types, same enum ordinals — enums serialize as ints). Fine for "both run my build" LAN play; fragile the moment builds drift. → *Cheap insurance: host sends `(CurrentVersion, type-map hash)` in the greeting reply; client refuses on mismatch with a human-readable error.*
- **Local/remote payload asymmetry**: `SendCommandToAllAsync` dispatches the *live object* to local handlers but a JSON *snapshot* to remote ones. A local handler that holds or mutates the message sees different semantics than a client. → *Document it on the bus interface; or serialize-then-locally-deserialize in DEBUG builds to flush out aliasing assumptions.*
- Hardening nits: no max payload length on read (a corrupt length prefix rents a huge buffer); rented send buffers aren't returned on serializer exceptions (pool-miss, not a leak); `CommandProtocol` allocates two 4-byte arrays per frame; in-game chat send path exists but the host handler is commented out (dead feature, §13.11).

### Serialization round-trip audit (the "will both ends work" check)

What crosses the wire, and verdicts:

| Payload | Verdict | Notes |
|---|---|---|
| `DataReference`, `TypeID` | ✅ | Public-field struct + readonly struct with matching ctor param — round-trips under Newtonsoft (covered by store/save tests). |
| `ModelID`/`UnitID`/`PlayerID`/`TaskID` (record structs wrapping Guid) | ✅ | Round-trip verified by `ModelIDTests`/`UnitIDTests`; positional record ctor matches. Keep avoiding ID-keyed dictionaries in serialized types, or add a converter first. |
| `Position`/`Float3`/`Float2` | ✅ | Public-property structs with matching ctors; exercised by beat serialization tests. (`Float3`'s private setters + ctor matching is Newtonsoft-compatible but brittle if a second ctor is added — note in passing.) |

| `TokenContainer` (unit/model rule state) | ✅ | `[JsonProperty]` private-field serialization; `TokenRoundTripTests` cover it; event subscriptions explicitly excluded by doc contract. |
| `PresentationBeat` subclasses in `PresentBeatMessage` | ⚠️ | Round-trips today (`PresentationBeatSerializationTests` cover all 7 beats, polymorphic via `TypeNameHandling.Auto`). Risk: `$type` carries the full type name — renaming/moving a beat class breaks old clients *silently* (discard behavior above). Mitigate with the unknown-type warning + version handshake. |
| `StageTaskRequestMessage`/`ReplyMessage` | ✅ | Type-name whitelist registry + explicit `typeof(TReply)` serialization for polymorphic replies. Request types not covered by tests (see §5 gaps) are the residual risk. |
| `StageTaskNotifyAwaitingMessage` | ⚠️ | Carries `DataBinding<PlayerSlotInfo>` — deserialization *requires* the slot's store entry to already exist client-side. | Lobby messages (chat, settings, player list, army lists) | ✅ | Simple records/strings; `GameSettings` is plain data. Enum fields (e.g. `EPlayerType`, `EChatMessageType`) ride as ints — fine same-build, see version note. |
| Saves over the lobby (resume flow) | ✅ | Host-only by design (`LobbyViewModel_Client.CanSaveGame => false` documented); save JSON itself audited in §9. |

**Bottom line:** everything that must round-trip today does (and the test suite proves the risky polymorphic parts). The hazards are *evolution* hazards — type renames, enum reorder, build skew — plus the binding-in-notification coupling. None require redesign; all are addressable with the handshake + warning + payload simplification above.

### Test coverage notes
Serialization is well tested; **transport has zero tests**. A loopback `FDGHost`+`FDGClient` fixture (real sockets on an ephemeral port) testing connect → frame echo → disconnect → mid-frame disconnect would cover the riskiest untested code in the repo. Add one interleaved-concurrent-send test and it will catch the write-lock bug deterministically.

**Score: 5/10** — a sound, debuggable wire design and genuinely working replication, undermined by concurrency holes (frame interleaving, connection-ID race, dispatch fragility) and silent-failure philosophy. The fixes are small relative to the payoff.

## 7. Presentation system (beats)

Stages emit semantic `PresentationBeat`s (`UnitMovedBeat`, `DiceRolledBeat`, `AttackBeat`, …) via `await context.Presenter.Present(beat)`. The presenter fans out to per-player `IPresentationSink`s (local render, or `NetworkedPresentationSink` → `PresentBeatMessage` to that client) and then waits the beat's nominal duration once, on an injected `IPresentationClock` (`Realtime` scaled, or `Instant` for headless/tests).

### Pros
- **This is the best-designed subsystem in the engine.** The separation is exactly right: engine owns *what happened* and *how long it nominally takes*; front-ends own *how it looks*; the clock owns *how nominal time maps to wall time*. Determinism for tests falls out (`InstantPresentationClock`), "slow mode" falls out (scale), and free-running play is guaranteed by construction (the engine never awaits renderer acknowledgement — and the docs *say so*).
- Documentation is exemplary throughout — every interface states its contract, including the serialization requirement on beats and the "logs and beats are siblings" relationship.
- Pacing knowledge is centralized in `PresentationDurations` with sensible derived durations (per-volley capped, move time ∝ distance clamped) and comments explaining the *experience* intent.
- The host paces once for everyone (single `clock.Wait` in `PresentationRelayer`), so clients can't build a backlog — a subtle correctness property handled correctly.
- The predecessor (`TempVisuals`) was retired cleanly rather than left half-alive.

### Cons → recommendations
- **Beat evolution is coupled to §6's silent discard**: a new beat type sent to an older client vanishes without trace (the `PresentBeatMessage` deserializes to null and is dropped). → *Covered by the §6 unknown-type warning + version handshake; nothing presentation-specific needed.*
- `PresentationRelayer` reaches into `PlayerSlotManager._playerSlots` (an `internal` field — there's a `PlayerSlots` property right next to it). → *Use the property; consider exposing an `IEnumerable<IPlayerController>` instead.*
- `NetworkedPresentationSink.OnBeat` fire-and-forgets `SendCommandToSingleAsync` — a send failure is unobserved (consistent with sink semantics, but worth a comment).
- `DiceRolledBeat` carries an `ERandomnessType`-style enum and dice histograms — int-enum wire fragility as per §6.
- Beats carry `Text` for CLI rendering, but a few beats' text and durations have no tests (only the contract and serialization do). → *Cheap: a table-driven test asserting every concrete beat has `NominalDuration >= 0` and non-throwing `Text`.*

### Novelty
Event-stream presentation with engine-paced semantic beats is a known pattern in replay/spectator systems and digital board games, but it's executed here unusually cleanly for a hobby codebase. The clock-scale abstraction subsuming "slow mode" is a nice touch.

### Test coverage notes
`PresentationContractTests` (emit-then-pace, ordering, cancellation), `PresentationRelayerTests` (fan-out), `PresentationBeatSerializationTests` (all beats round-trip), `AttackBeatPositionsTests` (tracer endpoints) — comprehensive for the machinery. Per-beat text/duration assertions are the only gap.

**Score: 9/10** — the reference-quality subsystem; dock one point for the evolution coupling and small encapsulation nits.

## 8. Rules systems (new `Rules/` + legacy `Special Rules/`)

The new system (`Rules/`, work item #042): rules are *data* — `SpecialRuleDefinition` bundles passive `HookEntry`s (hook ID + actor/subject seat + `Condition` + `Effect`s) and activated abilities; `CoreRuleCatalog` declares 19 rules; `RuleResolver` maps army-list names/aliases to definitions; stages fire hook contexts through `RuleEvaluator`, which returns `RuleOperation` queues folded into game state by typed sinks (`IRollModifierSink`, `IWoundIgnoreSink`, …) or run by `OperationExecutor`. Tokens (`TokenContainer` with clear-triggers) persist rule state across serialization. The old system (`Special Rules/`, 34 files): interface-per-situation (`ISpecialRule_Attacker`, …) with mostly-stub classes.

### Pros
- **The new architecture is the right one for this problem.** Declarative definitions + hook dispatch + operation queues means new rules are catalog entries, not stage edits; the suppression pass (Unstoppable cancels Regeneration; Rending/Bane compose it) solves rule-vs-rule interaction generically; seats (actor/subject) cleanly express "my Stealth vs. your shooting".
- **All 19 implemented rules work end-to-end and 17 have integration tests** through the real stages (hit modifiers, extra hits on 6s, Deadly multiplication, wound-ignores with suppression, Tough at creation, Scout/Ambush/Vanguard through deployment). The `TestRuleHarness` makes a new rule's test ~20 lines.
- `RuleValidator` + `HookContextCatalog` verify at registration that a rule's conditions/effects only demand capabilities its hook context actually provides — moving a whole class of errors from "mid-game crash" to "startup failure".
- Alias resolution preserving the requested display name ("Healing Pods (Regeneration)") shows attention to the army-builder UX, and the "names are the persisted form, definitions resolve at load" serialization stance (documented on `IUnit.RuleDefinitions`) is exactly right.
- Token lifetimes (`TokenClearTrigger` round/activation/manual) give temporal rule state a principled home.

### Cons → recommendations
- **Base `Condition.Evaluate`/`Effect.Apply` default to throwing `NotImplementedException`** — five stub conditions (`UnitHasRule`, `TargetHasRule`, `StatGreaterOrEqualTo`, `TargetMajorityHasTough`, `Or`) and three stub effects (`StatModifier`, `AddExtraWound`, `ConsumeToken`) are runtime bombs if a future catalog entry references them. None of the 19 current rules do, so it's latent. → *Make the validator reject definitions using not-yet-implemented members (a static "implemented" registry or a marker interface) so it fails at startup like everything else; or make the bases abstract and give stubs explicit throwing bodies so the unimplemented set is greppable.*
- **Three `RuleOperation`s are queued but never applied** (`MultiplyHits`, `ChargeImpactHits`, `ExtraMeleeWoundCount` are plain operations with no sink) — same latent-bomb class, blocked on the melee framework. → *Same validator treatment.*
- **The old system is nine-tenths corpse but still load-bearing in signatures**: `IUnit.SpecialRules`/`IModel.SpecialRules`/`Weapon`'s rule set are typed against old interfaces and *never populated* (`GetRealSpecialRulesFromArmyList` returns an empty list with a TODO); `CombatStage` still gathers `ICombatEffect`s from them (always none); old `Regeneration` contains real-looking logic against retired result types — actively misleading. → *Finish the migration: delete `Special Rules/` (keep a tag), remove the dead properties and the empty `GetReal…` shims, and let `RuleDefinitions` be the only rules surface. This is mostly deletion; estimate a half-day including parent-app compile fixes.*
- `RuleHookBus` is an acknowledged vestige kept for one harness smoke test. → *Delete with the migration.*
- The operation/sink vocabulary is growing fast (30+ operation records, 8 sink interfaces). It's manageable now, but each new mechanic adds a record + sink + fold site. → *Watch for the moment a generic "stat pipeline" (modifier lists folded at read time) would collapse several sinks; don't preempt it yet.*

### Novelty
Data-driven rule definitions with hook dispatch and operation queues is the standard architecture in serious digital card/wargame implementations (and engine-side it resembles an event-sourced effect system). Choosing it — and *landing* it with tests — is the most impressive engineering investment in the repo, even if the pattern itself is established.

### Test coverage notes
Excellent for implemented rules. Gaps: Very Fast and Slow have no tests (trivial with the harness — clone the Fast test); `RuleResolver` error paths (unknown rule name, bad argument count) are untested; no test pins "every catalog entry validates against its hook contexts" as a single sweep (one `[Test]` looping the catalog would catch the latent-bomb class above).

**Score: 7/10** — the new system alone is an 8.5; the unfinished demolition of the old one (dead-but-referenced surfaces, misleading stubs) and the latent NotImplemented bombs pull it down.

## 9. Save/Load

`GameSaveSerializer.Save` writes a versioned envelope: type-map fingerprint (full names + capacities) + every store entry as (reference, JSON). `Load` rebuilds an identically-shaped store, replays entries with a deferred-retry loop (entries whose `DataBinding` fields reference not-yet-recreated entries are retried next pass, with a stall detector), then re-wires the event subscriptions JSON constructors deliberately skip. `GameProgressData` (§3) re-enters the state machine at the right stage; army/terrain files (`ArmyListFile`, `TerrainLayoutFile`, `SpecialRuleRegistry`) handle content.

### Pros
- **The deferred-retry replay is the elegant move.** Cross-references between store entries make ordering a graph problem; instead of topo-sorting, the loader just retries failures until a pass makes no progress, then fails loudly with the last error. Simple, correct for DAGs, and the "a failed create writes nothing, so retry is safe" invariant is documented where it matters.
- Version check, type-map fingerprint with capacities (guaranteeing every saved index fits — fixed-size stores made *compatible* with saves), and a clear stall exception: the failure modes were thought through.
- The save is plain, indented JSON — debuggable and diffable, which for a hobby project is worth more than compactness.
- The post-load `RewireModelWoundSubscriptions` hook pairs with the documented "JSON ctor must stay order-independent" contract (§3) — the two halves of the design reference each other.
- Resume integrates with the lobby (slot re-crew with Local/AI choice) and the state machine (named top-level entry) rather than being a bolt-on.

### Cons → recommendations
- **Type names are the format**: `ResolveType` matches `FullName` against the engine assembly — renaming/moving any registered type (or a beat referenced inside saved JSON via `$type`) breaks every existing save with "can't resolve type". Acceptable pre-1.0, but it will bite silently. → *When the format next changes anyway, key the map by a stable string ID (`"model"`, `"unit"`) with a name→type registry; keep a `FullName` fallback for old saves.*
- **Version mismatch is a hard wall** (`!= CurrentVersion` throws). Fine at v1, but the first time you bump it, every save dies. → *Decide now: either commit to "saves don't survive versions" (then say so in the UI), or sketch a migration hook (`IGameSaveMigrator` from v(n) to v(n+1)) before v2 exists.*
- `SpecialRuleRegistry`/`ArmyListParser`/`TerrainLayoutLoader` have no direct tests, and their failure modes (unknown rule alias, malformed army JSON, negative quantities) surface as raw exceptions mid-lobby. → *A dozen table-driven parser tests; convert raw exceptions to a `(bool ok, string error)` shape the lobby can display.*
- The save captures the *store*, but anything living outside it is silently not saved — that's the design (and `GameProgressData` exists precisely to promote flow state into the store), but there's no guard against the next contributor adding engine state outside the store. → *One doc paragraph in `SaveLoad/` stating the rule: "if it must survive a save, it lives in the store."*

### Novelty
Snapshot-the-store with reference fixup is standard save architecture; the retry-replay instead of dependency sorting is a pragmatic, slightly unusual simplification that fits the small data size.

### Test coverage notes
`GameSaveLoadTests` covers round-trip, version/type validation, and rewiring; `GameProgressTests` covers resume data; `TokenRoundTripTests` covers rule state. Gaps: the content-file parsers above, and a "save mid-combat, load, finish the activation" integration test (the resume enum only covers stage granularity — worth pinning what's *intended* to be lost on load).

**Score: 8/10** — small, documented, and correct for its scope; loses points for rename fragility and untested content parsers.

## 10. AI & players

`IPlayerController` abstracts "a seat at the table": `LocalPlayerController` (human, in-process UI), `NetworkPlayerController` (remote; readiness handshake, networked sinks), `ComputerPlayerController` (assigns an AI resolver registry). The AI (`Ai/`, 14 files) is *a resolver registry like any other* — `AiResolverRegistryFactory` registers one AI resolver per request type, with `AiUnitClassifier` scoring units shooting/melee/hybrid to steer decisions.

### Pros
- **AI-as-resolvers is the §5 architecture paying off**: the AI plugs into the same seam as a human, can't desync (it answers the same requests), and works over the network for re-crewed save slots. No engine special-casing anywhere.
- The heuristics that exist are sensible and table-aware: movement picks charge vs. advance by unit classification and preserves shoot eligibility (with the same `-0.001f` float margin the validators use — consistency!); ranged targeting prefers uncovered targets with graceful fallback; consolidation respects table bounds; Ambush placement scans for legal >9"-from-enemies rows.
- `AiPlaceObjectsResolver`'s row-based deployment with cohesion-respecting stagger is genuinely solid placement code, and it's the one AI resolver with a test.
- The controller abstraction keeps readiness (`WaitUntilReadyAsync` via TCS, not polling) and message routing per-seat, which made hotseat and mixed human/AI lobbies possible.

### Cons → recommendations
- **11 of 12 AI resolvers have no tests.** The AI's contract is "always produce a *legal* answer" — an illegal one throws mid-game (or worse, silently degrades via the §5 error path into a failed request). Nothing enforces legality per resolver. → *One happy-path test per resolver asserting the answer validates (deployment in zone, move within cap, wound assignment complete). The request/validator machinery already exists; this is an afternoon with high regression value.*
- `AiYesNoResolver` answers **true to every yes/no in the game**, current and future — fine for "bring on reserves?", wrong the day a "sacrifice this unit?" prompt exists. → *Route yes/no requests through a small intent enum on the request (or per-request-name table) so the AI's defaults are explicit.*
- `LocalPlayerController`'s two-phase UI subscription (subscribe if `PlayerMessageUI` non-null, else defer to an event) has a race window and null-coalesces failures into silence. → *Pass the UI in construction order that guarantees availability, or make the subscription idempotent and re-run it on assignment (same pattern as `RewireModelWoundSubscriptions`).*
- `NetworkPlayerController.IsReady` is set from bus dispatch with no synchronization/idempotency (duplicate ready messages double-fire `OnReadyStateChanged`). → *Guard with an exchange (`if (Interlocked.Exchange(...)`) or simply ignore when already ready.*
- `PlayerSlotManager` had an off-by-one bounds check (**fixed, §13.7**); `PlayerSlot` carries a "kinda wanna use TeamID" TODO and a commented-out `RequestDecision` corpse. → *Delete the corpse; the TeamID idea is sound (matches the ID story of §3) but low priority.*
- `ComputerPlayerController` hardcodes `SlowMode = false` at compile time. → *Feed it from `GameSettings` (the presentation clock scale already solved this problem for humans — reuse it).*

### Novelty
Resolver-pattern AI (AI as an input device, not a parallel brain) is an established and underused pattern; good fit here. Heuristics are conventional utility-scoring.

### Test coverage notes
See cons — the resolver suite is the big gap; `AiUnitClassifier` scoring is also untested (pure function, trivial to pin).

**Score: 6/10** — right architecture, competent heuristics, but near-zero test safety net and several small concurrency/lifecycle rough edges in the controllers.

## 14. Summary & key recommendations

### Overall

This is a coherent engine with a genuinely good spine: **decisions as brokered requests** (§5), **presentation as paced semantic beats** (§7), **rules as data with hook dispatch** (§8), and **state in one replicable/saveable store** (§2's redeeming feature). Those four ideas compose — AI, networking, save/resume, and headless automation all fall out of the same seams, which is exactly what an architecture is for. The test infrastructure (§12) makes the implemented parts trustworthy.

The weaknesses cluster in three places: **concurrency at the network boundary** (a handful of races and missing locks, all small fixes), **failure observability** (async-void transitions, silent message discard, swallow-and-disconnect dispatch — the engine fails quietly when it fails), and **unfinished demolition** (old Special Rules, dead fields, commented corpses, stale CLAUDE.md — cheap to clear, costly to leave because it misleads readers, including future-you and AI assistants reading the repo).

Informal overall: **6.5/10** — above-average hobby-engine bones with reference-quality spots (presentation, request brokering), held back by hygiene and a thin safety net in precisely the code that runs multiplayer.

### Recommendations, ordered by effort vs. reward

**Tier 1 — hours each, outsized payoff**
1. **Make the bus survivable** (§6/§13.15–17): per-handler try/catch in dispatch, visible once-per-type warning for unknown messages, ignore unknown TaskIDs. *Turns "mystery disconnect" into "readable log line."*
2. **Network concurrency batch** (§5/§6, §13.13–14, 16): `RunContinuationsAsynchronously` on every TCS + `ConcurrentDictionary` for pending tasks + per-connection write semaphore + parameterized ConnectionID. Do as one change — the TCS fix removes the accidental serialization currently masking the others.
3. **Defuse the capacity bomb** (§2, §13.19): raise default capacities + startup assert (or make stores growable). *One realistic army list away from a crash today.*
4. **Update CLAUDE.md's stub list** (§13.12) and **delete the dead weight** (`FDGEntity`+`Components`, commented-out blocks, dead fields, `TEST_SINGLE_TURN`). *Cheapest possible improvement to repo truthfulness.*
5. **Split `Tests/` into its own project** (§1). Mechanical; unships NUnit/Moq from the game assembly.
6. **Pin the type-map order with a test** (§2) so a reorder fails CI instead of corrupting saves.

**Tier 2 — a day or two each, high value**
7. **Await through the state machine** (§4, §13.18): `Transition` → `Task`, surface one awaitable game Task with a top-level fault handler. *The single biggest reliability win in the codebase; everything else assumes stages can't fail silently.*
8. **Finish the rules migration** (§8): delete `Special Rules/`, remove the never-populated `SpecialRules` properties and empty shims, retire `RuleHookBus`. Mostly deletion; removes the most misleading code in the repo.
9. **Test the scary holes** (§12): TCP loopback fixture (incl. one concurrent-send test), AI resolver legality suite, `VictoryCalculationStage`. *These three target every High-risk row in the coverage map.*
10. **Implement `ValidateMovingThroughEnemyUnits`** (§11) — the machinery (segment-vs-circle, error enum) already exists.
11. **Version/type-map handshake on join + enums-as-strings on the wire** (§6) — cheap insurance before any build-skew testing happens.
12. **Catalog-validation sweep + reject unimplemented Conditions/Effects at startup** (§8) — converts the latent `NotImplementedException` bombs into startup errors.

**Tier 3 — multi-day / design decisions, schedule deliberately**
13. **Store simplification v2** (§2): name-keyed type map (kills positional fragility and the append-only rule), growable stores, single binding converter. Keep the store concept — it earns its keep — shed the ECS costume.
14. **Disconnect lifecycle** (§6/§10): fail a departed player's pending requests, surface it to stages, optionally AI-takeover their slot (the resolver architecture makes this almost free — that's the payoff of §5).
15. **Namespace unification under `FDG.*`** (§1) — one commit, coordinated with the parent app.
16. **Melee/fatigue/morale completion** (§4) — game-design work more than engineering; the rules system (§8) is ready to receive it.

### A note on what *not* to change

The request/resolver brokerage, the presentation beat stream, the rules catalog/dispatch design, and the save replay loop are all pulling their weight as designed. The instinct to distrust `GameDataStore` is half-right — distrust its *costume* (positional IDs, fixed arenas, reflection), not its *role* (single replication/persistence surface); the role is why save/load and networking were buildable by one person in spare time.
